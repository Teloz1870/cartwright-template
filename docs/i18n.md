# Internationalisation (i18n)

## Locales

Supported languages live in `brand.config.ts`:

```ts
locales: ["da", "en"] as const,
defaultLocale: "da",
```

- `defaultLocale` is the **base language** — the source text stored directly in DB fields, and the
  language `getDynamicTranslation` treats as "no translation needed".
- Add a language in one place, e.g. German:
  ```ts
  locales: ["da", "en", "de"] as const,
  ```
  `i18n/routing.ts` reads this, so `/de/...` routes and `hreflang` alternates appear automatically.
  A single-locale shop emits no `hreflang` (no misleading signal).

## Translating content

Storefront **UI strings** are managed via i18nexus (`messages/<locale>.json`).

Storefront **content** (Product, Category, Page, Service, blog Post) is translated in
`/admin/translations`:

- Each entity stores translations in a `translations` JSON field:
  `{ en: { title: "…" }, de: { … } }`.
- The editor shows the base text (read-only) and an editable field per locale, with AI
  auto-translate (`/api/admin/translate`).
- At render, `getDynamicTranslation(entity, field)` returns the current locale's translation,
  falling back to the base text.

### Translatable fields

| Entity | Fields |
|---|---|
| Product | name, description |
| Category | name, description |
| Page | title, body |
| Service | title, shortDescription, body |
| Post (blog) | title, excerpt, body |

## Known gap

Page, Service and blog Post **detail** pages render translations today. Product/Category
**storefront** rendering still shows base text (the editor saves translations, but the PLP/PDP
render path doesn't read them yet) — a planned follow-up.
